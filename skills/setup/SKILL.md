# Skill: /ak:setup

Work out how *this* repo does things, and write it down once so every other skill stops guessing.

Without this, `/ak:setup`'s siblings fall back to defaults — `main` as the base branch, `npm test` as the test command, Conventional Commits, GitHub. Those are right often enough to be dangerous and wrong often enough to matter.

## Detect first, ask second

Every question you ask is one the user has already answered somewhere in the repo. Go and read it.

| Fact | Where to look |
|---|---|
| Default branch | `git symbolic-ref refs/remotes/origin/HEAD`, falling back to `git branch --list main master develop` |
| Git host | `git remote get-url origin` |
| `gh` available and authenticated | `gh auth status` |
| Package manager | the lockfile — `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lockb` |
| Test / lint / build commands | `scripts` in `package.json`; otherwise `Makefile`, `justfile`, `pyproject.toml`, `Cargo.toml`, `go.mod` |
| E2E command | a Playwright/Cypress config or an `e2e`/`test:e2e` script |
| Formatter | a Prettier/Biome config, or the `format` script |
| Commit convention | `git log --oneline -30` — do the subjects match `type(scope): …`? |
| Language of commit and PR text | the same log, plus recent PR titles |
| Source and test layout | the directories the test command actually points at |

Only ask about what's left. **One round of questions, batched** — not an interview.

## Verify before recording

A command that doesn't run is worse than no command, because the skill that reads it will fail confidently.

- A `package.json` script exists → record it.
- A binary is claimed → check it resolves (`--version` or equivalent).
- Nothing verifiable → record `unknown` and say why. Never write a plausible default.

Don't *run* the test suite to check it works. Confirm it's defined; that's the boundary.

## Write `.ak/config.md`

Read the existing file first if there is one, and preserve anything you didn't change — the user may have hand-edited it, and their edit outranks your detection.

```markdown
# Project config — read by /ak: skills

Generated by /ak:setup on <date>. Hand edits are preserved; re-run to refresh.

## Repo
- Default branch: main
- Git host: github.com/<owner>/<repo>
- `gh` CLI: available, authenticated

## Commands
- Install: npm ci
- Test: npm test
- Lint: npm run lint
- Typecheck: unknown — no script found
- Build: npm run build
- E2E: unknown — no e2e runner found
- Formatter: npx prettier --write

## Conventions
- Commits: Conventional Commits
- Commit and PR language: English
- PR base branch: main

## Layout
- Source: src/
- Tests: evals/
- Plans: specs/
```

Drop any section where everything is unknown. A short honest file beats a long speculative one.

`## Commands` is more than prose: `npx ai-workflow-kit verify <slug> --final`
executes the `Test` / `Lint` / `Typecheck` / `Build` / `E2E` entries as the
global checks of a final verification, skipping any marked `unknown`. What you
record here is what the harness will actually run.

## Rules

- Never write a secret, token, or connection string into the config. It's a committed file.
- Don't record a preference nobody asked for. If no skill reads it, it doesn't go in.
- Report the path you wrote, and the facts you had to mark unknown — those are what the user might want to fill in by hand.
