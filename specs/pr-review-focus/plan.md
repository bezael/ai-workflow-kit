# Plan: Review focus — per-file "needs a human" level in /ak:pr

Status: done
Updated: 2026-09-13

## Goal
`/ak:pr` tells the reviewer which changed files need human attention and why, from a deterministic, explainable per-file level (HIGH / MEDIUM / LOW) built on the existing `risk` signal plus repo-declared sensitive paths and file kind.

## Context
Idea from a code-review paper the user read: not every file in a PR deserves the same human attention. Four `.md` files and one auth change should not get the same review budget. We keep **one PR** and put the attention map *inside* it; splitting into several PRs is offered only when the groups are provably independent, never by default (see Risks / decisions).

Three sources feed the level, in priority order:

| Source | Where it lives today | Level it produces |
|---|---|---|
| Sensitive paths (auth, billing, migrations, …) | **new** — `## Review` section of `.ak/config.md`, written by `/ak:setup` | always HIGH, reason names the matched pattern |
| Churn / fix history | exists — `bin/risk.js` (`high` / `medium` / `low` / `new`) | `high` → HIGH, `medium` → MEDIUM, `low` → LOW, `new` → MEDIUM ("new code, unknown risk") |
| File kind | **new** — built-in patterns for docs, lockfiles, fixtures | LOW ("docs only"), unless a sensitive pattern also matches |

Every level carries its reasons as text. The level orders attention; it is never itself a finding.

## Risks / decisions
- **One PR with a focus map, not N PRs by risk.** Splitting by risk level produces PRs that are not logical units: the docs describe code that is not merged yet, or the auth change ships undocumented, and stacked PRs must be rebased in order. The paper's gain is *attention allocation*; a table in the body delivers that without changing anyone's git flow. Splitting stays an **offer**, made only when a LOW-only group references no symbol of the HIGH group, and only at file granularity (hunk-level splits are where an agent corrupts a diff).
- **Deterministic core, LLM only for the fallback.** `reviewNeed` lives in `bin/risk.js` so it is unit-tested and identical across Claude Code / Antigravity / Codex. The skill only reasons on top when `npx` is unavailable, and it says so in the body.
- **Sensitive wins over file kind.** `docs/auth/threat-model.md` matching `docs/auth/**` as sensitive must be HIGH even though it is a `.md`. Rule order: sensitive → docs-only → history.
- **`new` maps to MEDIUM, not LOW.** Same principle the risk signal already states: no history is unknown risk. A brand-new code file is not a skim.
- **Tests keep their history level.** A weakened assertion is a real risk, so test files are not forced LOW; only docs, lockfiles and fixtures are.
- **`--focus` is a view, not a new subcommand.** The `risk` table `/ak:review` reads stays byte-identical without the flag; JSON gains fields, which is backwards compatible.
- **Glob matching without a dependency.** The kit has zero runtime deps and `**` / `*` / `?` cover every pattern setup will write. A full `minimatch` is out of proportion.
- **Labels are opt-in by existence.** `gh pr create --label` fails if the label does not exist, so the skill applies it only when `gh label list` shows it, and otherwise mentions it in the body. No label creation.
- **`.ak/config.md` stays committed and secret-free.** Sensitive *paths* are not secrets; the setup rule about tokens is unchanged.
- Rejected: a numeric 0–100 score. Three levels with a stated reason are what a reviewer can act on; a number invites false precision and arguments about thresholds.
- Rejected: LLM-computed sensitivity per file at PR time. Not reproducible across runs, not testable, and it would contradict the "evidence, not verdict" stance the risk signal already documents.

## Not included in this plan
- Automatic PR splitting. Revisit after the focus table has been used on real PRs and we know whether the levels are trusted.
- Hunk-level (intra-file) attention levels. File granularity only.
- An eval fixture for `/ak:pr` (`pr` stays in `src/eval-coverage.json` pending; the reason "no branch fixture" is unchanged by this work).
- Reading CODEOWNERS or GitHub required-reviewer rules as a sensitivity source. Plausible follow-up, different data source.
- Any change to the hooks.
